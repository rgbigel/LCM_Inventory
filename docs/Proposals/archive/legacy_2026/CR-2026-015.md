# CR-2026-015: Mandate Universal install/ Directory and Installation.md Runbook Standard

- **Origin Repository**: `Workspace_Inventory`

## 1. Executive Summary & Intent

End users and operators do not execute applications or automation tools directly from working Git clone repositories. Instead, repositories deploy their operational payloads to dedicated installation target directories on the system.

This Change Request formalizes a mandatory **`install/`** directory standard across all LCM-governed repositories, centered around an authoritative, step-by-step **`Installation.md`** lifecycle runbook.

---

## 2. Core Architectural Invariants

### A. Dedicated `install/` Directory Standard
* Every governed repository `MUST` maintain an `install/` directory at the repository root:
  ```
  <Repo>/
  ├── install/
  │   ├── Installation.md          # Primary installation & lifecycle runbook
  │   ├── 01-Prerequisites.md      # (Optional) Sub-phase document for complex setups
  │   ├── 02-Configuration.md      # (Optional) Sub-phase document for complex setups
  │   └── 03-Deployment.md         # (Optional) Sub-phase document for complex setups
  ```
* For standard components, a single `install/Installation.md` suffices. If installation complexity warrants it, steps are cleanly split into numbered sub-documents within `install/`, orchestrated by `Installation.md`.
* `install/` contains purely procedural runbooks and installation automation scripts; it contains **no `README.md`**.

### B. Target Installation Layout Architecture
* In the user-defined installation target directory (e.g. `D:\Tools\<Component>` or `$env:ProgramFiles\<Component>`):
  * **Immediate User-Exposed Parts**: Primary modules, user CLI wrappers, or main executables reside top-level.
  * **Subdirectory Encapsulation**: Internal maintenance scripts, background runners, utilities, and helper tools are organized into subdirectories (e.g. `tools/`, `maintenance/`, `bin/`).

### C. Cross-Repository Dependency Invariant
* External and shared dependencies (such as `SharedModules`, `Workspace_Inventory`, or external CLIs) `MUST` be represented strictly as **Prerequisite Assertions** and **Linkage Steps**.
* `Installation.md` `MUST NOT` duplicate internal architectural descriptions, classes, or code logic of foreign repositories.

---

## 3. Standard Procedural Lifecycle Schema

Every `install/Installation.md` document conforms to the 7-phase procedural lifecycle:

1. **Prerequisites & Environmental Dependencies**:
   - Host runtime (PowerShell 7+, OS build, hardware, elevation context).
   - Cross-repository links (`SharedModules` paths, module auto-loading setup).
2. **Pre-Installation Readiness Checks**:
   - Non-destructive preflight validation commands (`Test-*Prerequisites.ps1`).
3. **Configuration & Customization**:
   - Parameters, configuration files (`.lcm/config.json`, ini/json settings, environment variables).
4. **Step-by-Step Installation Procedure**:
   - Deterministic sequential commands to copy binaries, configure junctions, register scheduled tasks, or deploy shortcuts.
5. **Post-Installation Verification & Health Tests**:
   - Smoke tests and automated checks confirming operational readiness.
6. **Version Update & Migration Procedures**:
   - Data migration steps, configuration reconciliation, cache invalidation, and rollback steps.
7. **Uninstallation & Teardown**:
   - Complete, residue-free teardown commands.
